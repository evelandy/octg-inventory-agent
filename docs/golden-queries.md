# Golden Queries

Questions with known answers. They are the source of truth for checking that the data is correct and, later, that the agent answers inventory questions correctly. There are two sets:

| | Part 1: seeded data | Part 2: fixture data |
|---|---|---|
| Data | Generated by Faker (`faker.seed(100)`), 218 joints | Hand-written SQL, 12 joints |
| Database | `octg_inventory` | `octg_fixtures` |
| Queries | [`server/src/db/golden-queries.sql`](../server/src/db/golden-queries.sql) | [`server/src/db/fixtures/golden-queries-fixture.sql`](../server/src/db/fixtures/golden-queries-fixture.sql) |
| Answers change when | the seed code, seed number or Faker version changes | someone edits the fixture file |
| Good for | realistic volume | exact answers you can check by hand, and edge cases the seed doesn't produce |

# Part 1: Seeded data

## Dataset these answers belong to

| | |
|---|---|
| Seed script | `server/src/db/seeders/inventory.ts` with `faker.seed(100)` |
| Seed commit | _not yet committed record the hash here when it is_ |
| Recorded | 2026-10-15 |
| Size | 218 joints (58 casing, 50 tubing, 60 production casing, 50 pup joints), 436 inspections, 30 specs, 4 yards, 10 racks, 10 heats |

The answers stay the same across re-seeds as long as the seed number and seed code don't change (verified by seeding twice and comparing). UUIDs and `faker.date.past()` dates differ between runs, so no question depends on an id or an exact date.

## How to check

From the repo root, rebuild and run all five:

```bash
docker compose down -v && docker compose up -d --wait
cd server && npm run migrate && npm run seed:inventory && cd ..
docker compose exec -T db psql -U octg -d octg_inventory -f - < server/src/db/golden-queries.sql
```

Compare each result with the expected answer below. If one differs, either the seed changed on purpose (recompute and update this file in the same commit) or something broke.

## Q1. Available stock of one spec in one yard

**Question:** How many available joints of 9-5/8" 40# J55 casing are in the Houston yard, and how many feet?

**Expected:** **4 joints, 159.11 ft**

**Tests:** filtering by spec and status; finding "Houston" in `yards.region` (yard names are "Test Yard …"); summing `inventory_summary` across racks, since the view has one row per rack.

## Q2. Inventory by yard and product type

**Question:** How many joints and feet of each product type does each yard hold?

**Expected:**

| Yard | Region | Product type | Joints | Feet |
|---|---|---|---|---|
| Test Yard 2-3 | Pleasanton Yard (Eagle Ford) | casing | 10 | 295.77 |
| Test Yard 2-3 | Pleasanton Yard (Eagle Ford) | tubing | 10 | 292.52 |
| Test Yard 2-3 | Pleasanton Yard (Eagle Ford) | production_casing | 12 | 335.47 |
| Test Yard 2-3 | Pleasanton Yard (Eagle Ford) | pup_joint | 10 | 303.27 |
| Test Yard 4-2 | Houston Yard (Gulf Coast) | casing | 48 | 1344.02 |
| Test Yard 4-2 | Houston Yard (Gulf Coast) | tubing | 40 | 1210.20 |
| Test Yard 4-2 | Houston Yard (Gulf Coast) | production_casing | 48 | 1308.65 |
| Test Yard 4-2 | Houston Yard (Gulf Coast) | pup_joint | 40 | 1202.09 |

**Tests:** grouping into several rows. Product types sort in **enum order** (casing, tubing, production_casing, pup_joint), not alphabetically, because Postgres sorts an enum by the order its values were declared. Yards with no joints (Test Yard 1-1, Test Yard 2-4) don't appear. Joints without a rack aren't in any yard, so they're excluded.

## Q3. Quarantined joints by location

**Question:** How many joints are quarantined, and where are they?

**Expected:**

| Yard | Joints | Feet |
|---|---|---|
| Test Yard 2-3 | 12 | 326.93 |
| Test Yard 4-2 | 63 | 1870.53 |

**Tests:** status filter; joints with no yard would show as "(not in a yard)" rather than being dropped. All seeded joints are currently on racks, so that row doesn't appear yet.

## Q4. Heat traceability

**Question:** Which mill made heat H1789, and where are those joints now?

**Expected:** **P2 Steel Works-3.** All **42** joints are in Test Yard 2-3, rack B-01-3, `on_rack`.

**Tests:** joint → heat → mill traceability, plus current location. Heat numbers are unique per mill, not globally; if two mills used H1789, both would appear.

## Q5. Failed latest inspection

**Question:** How many joints failed their most recent inspection, and how many of those are still marked available?

**Expected:** **91 joints** failed their latest inspection; **28** of them are still `available`.

**Tests:** "most recent" means latest `inspected_at` (via `joint_latest_inspection`), not the last row entered. The 28 is a data-consistency finding: joints that probably should be quarantined.

## How the answers were verified

Each answer was calculated twice by different routes, and both agreed:

| | Golden query uses | Cross-check used |
|---|---|---|
| Q1–Q3 | `inventory_summary` view | `COUNT`/`SUM` directly on `joints`, `racks`, `yards`, `pipe_specs` |
| Q4 | Joins with `GROUP BY` | Nested subqueries on `heats` and `mills` |
| Q5 | `joint_latest_inspection` view | `ROW_NUMBER() OVER (PARTITION BY joint_id …)` on `inspections` |

# Part 2: Fixture data

The data is hand-written in [`server/src/db/fixtures/inventory-fixture.sql`](../server/src/db/fixtures/inventory-fixture.sql): 2 mills, 3 heats, 3 specs, 3 yards (one empty), 3 racks, 12 joints (`F-001` to `F-012`) and 12 inspections. Every expected answer below was worked out by hand from that file before running the queries, and the queries then returned exactly those answers.

The fixture file includes cases the Faker seed doesn't produce: the same heat number at two mills, joints with no rack (in transit and at the mill), joints never inspected, a backdated inspection, an empty yard, and one spec spread across two racks.

## How to check

From `server/`, rebuild the fixture database (it's separate from `octg_inventory`, which is left untouched):

```bash
npm run db:fixtures
```

Then, from the repo root:

```bash
docker compose exec -T db psql -U octg -d octg_fixtures -f - < server/src/db/fixtures/golden-queries-fixture.sql
```

The fixture file stops with an error if any row fails to load (for example a misspelled spec tag), so a partial dataset can't produce misleading answers.

## F1. Available stock across two racks

**Question:** How many available joints of 5-1/2" 17# L80 casing are in the Houston yard, and how many feet?

**Expected:** **3 joints, 120.00 ft** (F-001 40.00 + F-002 40.50 on rack H-01, F-005 39.50 on rack H-02)

**Tests:** summing `inventory_summary` across racks. Excludes F-003 (reserved), F-011 (in transit, so not in the yard) and F-008 (Midland).

## F2. Joints not in a yard

**Question:** Which joints are not in a yard right now, and where are they?

**Expected:**

| Joint | Location | Status | Length |
|---|---|---|---|
| F-011 | in_transit | reserved | 40.25 |
| F-012 | at_mill | available | 29.75 |

**Tests:** joints with no rack. An answer that only looks through racks and yards misses both.

## F3. Never inspected

**Question:** Which joints have never been inspected?

**Expected:** **F-004, F-007, F-012**

**Tests:** `LEFT JOIN` with `IS NULL` on the right side. `joint_latest_inspection` can't answer this, because joints with no inspections aren't in it.

## F4. Heat number used by two mills

**Question:** Which mill made heat H100, and how many joints and feet came from it?

**Expected:**

| Mill | Joints | Feet |
|---|---|---|
| Alpha Mill | 5 | 201.25 |
| Bravo Mill | 4 | 142.25 |

**Tests:** heat numbers are unique per mill, not globally. A correct answer names both mills instead of picking one.

## F5. Latest inspection, with a backdated entry

**Question:** Which joints failed their most recent inspection, and what is their status now?

**Expected:**

| Joint | Status | Failed on |
|---|---|---|
| F-002 | available | 2026-06-15 |
| F-006 | quarantined | 2026-07-01 |
| F-009 | quarantined | 2026-07-20 |

**Tests:** F-008 must **not** appear. Its `fail` was entered last but dated 2026-01-15, before its 2026-08-01 `pass`. F-002 is the consistency finding: failed, but still available.
