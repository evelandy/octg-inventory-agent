# Golden Queries

Known-answer queries: questions with exact expected results. They are the source of truth for checking that the data is correct and, from Sprint 1, for comparing the agent's plain-English answers. There are two sets:

| | Part 1: seeded data | Part 2: fixture data |
|---|---|---|
| Data | Generated by `npm run seed` (Faker seed 100, anchor date 2026-10-01), 246 joints | Hand-written SQL, 12 joints |
| Database | `octg_inventory` (the database the agent uses) | `octg_fixtures` |
| Queries | [`server/src/db/golden-queries.sql`](../server/src/db/golden-queries.sql) | [`server/src/db/fixtures/golden-queries-fixture.sql`](../server/src/db/fixtures/golden-queries-fixture.sql) |
| Answers change when | the seed code, seed number, anchor date or Faker version changes | someone edits the fixture file |
| Good for | the scenarios the agent is tested against, at realistic volume | exact answers you can check by hand |

Each entry below has an ID, the question, the expected result, and a note on what it tests. In the `.sql` files, each query has a matching `\echo` line and one read-only `SELECT`.

# Part 1: Seeded data

## Dataset these answers belong to

| | |
|---|---|
| Seed script | `server/src/db/seeders/inventory.ts`, run with `npm run seed` |
| Determinism | `faker.seed(100)` and anchor date **2026-10-01** (`faker.setDefaultRefDate`); no value comes from the real clock |
| Seed commit | ` ` |
| Recorded | 2026-10-19 |
| Size | 4 yards, 10 racks, 4 mills, 10 heats, 30 specs, 246 joints, 411 inspections |
| Data fingerprint | `81aadfe482b5ef6ed96e204bc72a1089` (from `npm run seed:check`) |

**Overdue** means the latest inspection is more than 12 months before the anchor date (before 2025-10-01), or the joint has no inspections. Queries use the anchor date as a literal, never `now()`, so the answers don't drift as real time passes.

## How to check

From `server/`, rebuild from empty and run the checks and the queries:

```bash
cd .. && docker compose down -v && docker compose up -d --wait && cd server
npm run migrate && npm run seed
npm run seed:check
docker compose exec -T db psql -U octg -d octg_inventory -f - < src/db/golden-queries.sql
```

`npm run seed:check` should show only `PASS` rows and the fingerprint above. If the fingerprint differs, the seed's data changed: either on purpose (recompute every answer and update this file in the same commit) or by accident.

## Q1. Available stock of one spec in one yard

**Question:** How many joints of 5-1/2" 20# P110 are available in Houston Yard, and how many feet?

**Expected:** **6 joints, 249.69 ft**

**Tests:** filtering by spec, status and yard; summing `inventory_summary` across racks (the joints are on racks A-01 and A-02); leaving out pup joints of the same size. The one Houston joint of this spec that is reserved is not counted.

## Q2. On hand vs. available

**Question:** How much 13-3/8" 54.5# J55 casing do we have on hand, and how much is available?

**Expected:** **6 on hand, 0 available** (4 reserved, 2 quarantined)

**Tests:** the difference between on hand (every status) and available (status `available` only). A correct answer says the pipe exists but none of it can be used.

## Q3. Which yards have a spec available

**Question:** Which yards have 3-1/2" 9.3# L80 tubing available, and which do not?

**Expected:**

| Yard | On hand | Available |
|---|---|---|
| Houston Yard | 3 | 0 |
| Midland Yard | 0 | 0 |
| Pleasanton Yard | 0 | 0 |
| Williston Yard | 5 | 5 |

**Tests:** answering for yards that have none (a `LEFT JOIN` from `yards`). Only Williston has it available; Houston has it on hand but all reserved.

## Q4. Overdue inspections by yard

**Question:** How many joints are overdue for inspection, by yard?

**Expected:**

| Yard | Overdue | Never inspected | Last inspected over 12 months ago |
|---|---|---|---|
| Houston Yard | 15 | 4 | 11 |
| Midland Yard | 13 | 6 | 7 |
| Pleasanton Yard | 6 | 2 | 4 |
| Williston Yard | 6 | 2 | 4 |

40 joints in total. None of the 5 joints without a rack are overdue, so no "(not in a yard)" row appears.

**Tests:** the business rule that a never-inspected joint counts as overdue; measuring from the anchor date literal.

## Q5. Heat and mill traceability

**Question:** Which heat and mill does joint J-00042 trace back to?

**Expected:** heat **H24C2231**, **Prairie Pipe Works** (Tulsa, OK). The joint's spec is `CSG-9.625-36-J55-STC`.

**Tests:** joint → heat → mill.

## Q6. Failed latest inspection

**Question:** How many joints failed their most recent inspection, and how many of those are still marked available?

**Expected:** **50 joints** failed their latest inspection; **20** of them are still `available`.

**Tests:** "most recent" means latest `inspected_at` (via `joint_latest_inspection`), not the last row entered. The 20 is a data-consistency finding: joints that probably should be quarantined.

## How the answers were verified

Each answer was produced twice, across two separate runs of `npm run seed` (identical), and calculated again by a different route (matching):

| | Known-answer query uses | Cross-check used |
|---|---|---|
| Q1 | `inventory_summary` | `COUNT`/`SUM` on `joints`, `racks`, `yards`, `pipe_specs` |
| Q2 | `joints` with `FILTER` | `inventory_summary` grouped by status |
| Q3 | `yards` `LEFT JOIN` `racks`/`joints` | `inventory_summary` grouped by yard |
| Q4 | `MAX(inspected_at)` per joint | `NOT EXISTS` an inspection on or after 2025-10-01 |
| Q5 | Joins | Nested subqueries |
| Q6 | `joint_latest_inspection` view | `ROW_NUMBER() OVER (PARTITION BY joint_id …)` on `inspections` |

# Part 2: Fixture data

The data is hand-written in [`server/src/db/fixtures/inventory-fixture.sql`](../server/src/db/fixtures/inventory-fixture.sql): 2 mills, 3 heats, 3 specs, 3 yards (one empty), 3 racks, 12 joints (`F-001` to `F-012`) and 12 inspections. Every expected answer below was worked out by hand from that file before running the queries, and the queries then returned exactly those answers.

The fixture file includes cases the Faker seed doesn't produce: the same heat number at two mills, joints with no rack (in transit and at the mill), joints never inspected, a backdated inspection, an empty yard, and one spec spread across two racks.

## How to check

From `server/`, rebuild the fixture database (it's separate from `octg_inventory`, which is left untouched):

```bash
npm run db:fixtures
```

Then, from the repo root:

```bash
docker compose exec -T db psql -U octg -d octg_fixtures -f - < server/src/db/fixtures/golden-queries-fixture.sql
```

The fixture file stops with an error if any row fails to load (for example a misspelled spec tag), so a partial dataset can't produce misleading answers.

## F1. Available stock across two racks

**Question:** How many available joints of 5-1/2" 17# L80 casing are in the Houston yard, and how many feet?

**Expected:** **3 joints, 120.00 ft** (F-001 40.00 + F-002 40.50 on rack H-01, F-005 39.50 on rack H-02)

**Tests:** summing `inventory_summary` across racks. Excludes F-003 (reserved), F-011 (in transit, so not in the yard) and F-008 (Midland).

## F2. Joints not in a yard

**Question:** Which joints are not in a yard right now, and where are they?

**Expected:**

| Joint | Location | Status | Length |
|---|---|---|---|
| F-011 | in_transit | reserved | 40.25 |
| F-012 | at_mill | available | 29.75 |

**Tests:** joints with no rack. An answer that only looks through racks and yards misses both.

## F3. Never inspected

**Question:** Which joints have never been inspected?

**Expected:** **F-004, F-007, F-012**

**Tests:** `LEFT JOIN` with `IS NULL` on the right side. `joint_latest_inspection` can't answer this, because joints with no inspections aren't in it.

## F4. Heat number used by two mills

**Question:** Which mill made heat H100, and how many joints and feet came from it?

**Expected:**

| Mill | Joints | Feet |
|---|---|---|
| Alpha Mill | 5 | 201.25 |
| Bravo Mill | 4 | 142.25 |

**Tests:** heat numbers are unique per mill, not globally. A correct answer names both mills instead of picking one.

## F5. Latest inspection, with a backdated entry

**Question:** Which joints failed their most recent inspection, and what is their status now?

**Expected:**

| Joint | Status | Failed on |
|---|---|---|
| F-002 | available | 2026-06-15 |
| F-006 | quarantined | 2026-07-01 |
| F-009 | quarantined | 2026-07-20 |

**Tests:** F-008 must **not** appear. Its `fail` was entered last but dated 2026-01-15, before its 2026-08-01 `pass`. F-002 is the consistency finding: failed, but still available.
